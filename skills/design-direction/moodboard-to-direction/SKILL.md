# Moodboard to Direction

Translate references into design decisions for the user's actual project. Do not redesign or edit a live file unless asked.

## Inputs

Read the brief if provided: audience, primary user task, screen or flow, and constraints such as existing components, brand assets or accessibility. Inspect the actual images, either in Figma if accessible or via exports/uploads. If an essential input is missing, ask one focused question. If Figma cannot be opened, ask for exported frames; do not infer visual details from the link or file names.

## Method

1. Label what you can see by reference or region. Identify recurring choices in typography, composition, spacing, density, colour and imagery only where relevant. Separate observed details from interpretation and proposed motion.
2. Translate each useful observation into a project-specific rule and tie it to the user task. State what not to borrow. Do not clone a distinctive layout, logo, artwork or identity. Prefer the project's existing type, tokens and components when they can express the chosen direction.
3. Propose two directions that differ in hierarchy, layout, density or use of imagery, not just palette. If the user already picked a direction, refine it instead. Recommend one and name the trade-off.
4. Make the recommendation testable on one screen. For a small site, focus on the mobile main action; for a complex app, include a realistic data state and note any readability or accessibility questions. Do not claim checks passed unless performed.

## Output

Return a one-page direction: goal, observed references, borrow/avoid decisions, options, recommendation, and a concrete first frame with two checks. Label unverified assumptions. Distinguish suggested design rules from confirmed project tokens. Stop before token creation, Figma changes or implementation unless requested.

For criteria to evaluate a first run, see [pilot cases](references/pilot-cases.md).
